Audit and prepare the Orgni monorepo so that:

* `apps/web` deploys reliably to Vercel.
* `apps/api` deploys reliably to Azure Container Apps.
* `apps/worker` deploys independently to Azure Container Apps.
* Local, staging and production environments remain consistent.

Do not change product behaviour unless required to fix deployment issues.

## 1. Inspect the repository

Before changing anything:

1. Inspect the monorepo structure, package manager, framework versions and build scripts.
2. Identify the frontend framework and rendering mode.
3. Identify the backend framework, entry point and runtime.
4. Identify all environment variables used by the web, API and worker.
5. Identify any code that depends on local files, localhost URLs or development-only behaviour.
6. Produce a concise deployment-risk report.

## 2. Prepare `apps/web` for Vercel

Ensure `apps/web` can be configured as the Vercel project root directory.

Required checks:

* The frontend builds from a clean installation.
* The build does not rely on files outside the declared monorepo dependencies.
* Internal packages are correctly declared in `package.json`.
* Turborepo build dependencies are correct.
* Production builds do not use localhost URLs.
* Server-only secrets are never exposed to the browser.
* Browser-accessible environment variables use the framework’s required public prefix.
* API URLs are loaded from environment variables.
* Preview and production deployments can use different backend URLs.
* Routing, redirects and rewrites work in production.
* Static assets and image paths work from the deployed domain.
* Authentication callbacks use environment-based URLs.
* CORS and cookie behaviour support the Vercel frontend and Azure backend being on separate domains.
* The application does not require persistent local disk storage.
* The frontend has a clear production start and build process.
* Type-checking and linting run before deployment.

Add or fix:

```text
apps/web/package.json
apps/web/vercel.json          # Only when necessary
apps/web/.env.example
```

Expected environment variables should include appropriate equivalents of:

```env
NEXT_PUBLIC_API_URL=
NEXT_PUBLIC_APP_URL=
AUTH_SECRET=
AUTH_CALLBACK_URL=
```

Do not place real secrets in committed files.

Configure root scripts so these commands work:

```bash
npm run dev --workspace=apps/web
npm run build --workspace=apps/web
npm run lint --workspace=apps/web
npm run typecheck --workspace=apps/web
```

The production frontend must communicate only with the configured Azure API URL.

## 3. Prepare `apps/api` for Azure

Prepare the API for Azure Container Apps.

The API must:

* Run inside a Linux container.
* Listen on `0.0.0.0`.
* Read the port from `PORT`.
* Avoid assumptions about a fixed port.
* Be stateless.
* Avoid storing uploads or generated files permanently inside the container.
* Use Azure Blob Storage or an abstraction for persistent files.
* Use environment variables for all external services.
* Shut down gracefully.
* Handle termination signals.
* Expose health endpoints.
* Produce structured logs to standard output.
* Include request or correlation IDs.
* Avoid development reloaders in production.
* Run database migrations through a separate controlled command.
* Support horizontal scaling without relying on in-memory session state.

Required endpoints:

```http
GET /health
GET /health/ready
GET /version
```

Health behaviour:

* `/health` confirms that the process is alive.
* `/health/ready` checks required dependencies such as the database and Redis.
* Health responses must not expose secrets or sensitive infrastructure details.

Add or fix:

```text
apps/api/Dockerfile
apps/api/.dockerignore
apps/api/.env.example
apps/api/package.json
```

Use a multi-stage Docker build where appropriate.

The final image should:

* Contain only production dependencies and compiled output.
* Run as a non-root user where practical.
* Have a clear production command.
* Avoid copying unnecessary repository files.
* Build successfully from the monorepo root.

Expected variables should include suitable equivalents of:

```env
NODE_ENV=production
PORT=8080
DATABASE_URL=
REDIS_URL=
AZURE_STORAGE_CONNECTION_STRING=
AZURE_STORAGE_CONTAINER=
CORS_ORIGINS=
AUTH_SECRET=
LOG_LEVEL=
APP_VERSION=
```

## 4. Prepare `apps/worker` for Azure

The worker must deploy separately from the API.

The worker should:

* Use the same shared contracts and configuration packages.
* Process asynchronous and long-running jobs.
* Not expose public application routes.
* Include a lightweight health mechanism where supported.
* Shut down gracefully.
* Stop accepting new work during termination.
* Finish or safely return active jobs to the queue.
* Use persistent queues rather than in-memory queues.
* Avoid duplicate processing through idempotency controls.
* Support retries and dead-letter handling.
* Produce structured logs.

Add or fix:

```text
apps/worker/Dockerfile
apps/worker/.dockerignore
apps/worker/.env.example
apps/worker/package.json
```

## 5. Configure cross-origin communication

The Vercel frontend and Azure API will use different domains.

Prepare the API for origins such as:

```text
https://app.orgni.olyxee.com
https://*.vercel.app
```

Do not allow all origins in production.

Implement environment-based CORS configuration.

When authentication uses cookies:

* Use secure cookies in production.
* Configure an appropriate `SameSite` policy.
* Confirm whether credentials must be enabled in CORS.
* Avoid domain settings that break Vercel preview deployments.
* Add CSRF protection where required.

When authentication uses bearer tokens, document the expected frontend flow.

## 6. Shared configuration

Use `packages/config` to validate environment variables when each application starts.

Requirements:

* Separate web, API and worker schemas.
* Fail immediately when required production variables are missing.
* Allow sensible local development defaults only where safe.
* Never log secret values.
* Do not make backend-only variables available to the frontend bundle.

## 7. Docker and local parity

Add a local development configuration for:

```text
web
api
worker
postgres
redis
```

The local environment should closely match production without making local development unnecessarily difficult.

Ensure these commands work:

```bash
docker compose up --build
npm install
npm run dev
npm run build
npm run lint
npm run typecheck
npm run test
```

## 8. CI validation

Create or update GitHub Actions workflows to validate deployments before merging.

Pull-request checks must include:

* Dependency installation with the lockfile.
* Formatting check.
* Linting.
* Type-checking.
* Unit tests.
* Shared contract tests.
* Frontend production build.
* API Docker build.
* Worker Docker build.
* Detection of accidentally committed secrets.

For the backend, confirm that the built containers start and pass their health checks.

Do not automatically deploy production from pull requests.

## 9. Documentation

Create deployment documentation covering:

```text
docs/development/local-setup.md
docs/deployment/vercel.md
docs/deployment/azure.md
docs/deployment/environment-variables.md
```

The Vercel guide must explain:

* Project root directory.
* Install command.
* Build command.
* Output configuration where relevant.
* Environment variables.
* Preview deployment behaviour.
* Custom domain configuration.

The Azure guide must explain:

* Building API and worker images.
* Pushing images to Azure Container Registry.
* Creating separate Container Apps.
* Configuring secrets and environment variables.
* Setting ingress for the API.
* Keeping worker ingress disabled.
* Configuring health probes.
* Connecting PostgreSQL, Redis and Blob Storage.
* Running database migrations.
* Rolling back to an earlier container revision.

## 10. Acceptance criteria

The task is complete only when:

1. `apps/web` builds successfully from a clean checkout.
2. `apps/web` is ready to deploy with its Vercel root set to `apps/web`.
3. The frontend contains no hardcoded local API URL.
4. The API Docker image builds from the monorepo root.
5. The API container starts using only environment configuration.
6. The API listens on `0.0.0.0:$PORT`.
7. API health endpoints return correct statuses.
8. The worker Docker image builds and starts independently.
9. API and worker containers shut down gracefully.
10. Frontend-to-backend CORS is restricted and configurable.
11. No secret values are committed.
12. CI validates all three applications.
13. Deployment instructions can be followed by another engineer without undocumented steps.

After completing the work, provide:

1. The deployment-readiness issues found.
2. The files changed.
3. The final environment-variable matrix.
4. The exact Vercel project settings.
5. The exact API and worker container commands.
6. Remaining Azure resources that must be provisioned manually.
7. Any unresolved risks.
