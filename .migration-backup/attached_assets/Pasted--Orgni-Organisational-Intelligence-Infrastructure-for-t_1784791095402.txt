# Orgni: Organisational Intelligence Infrastructure for the Agentic Enterprise

## Abstract

Artificial intelligence is moving from isolated assistants toward systems that can retrieve information, use tools, coordinate work and perform actions across organisations. However, the ability to build an AI agent is advancing faster than the ability of organisations to provide those agents with reliable operational context.

Most organisations do not maintain a single, current and machine-readable representation of how they operate. Their knowledge is fragmented across documents, databases, emails, policies, workflow systems and employees. As a result, every new application, AI agent, transformation project or consulting engagement must reconstruct part of the organisation from the beginning.

This creates duplicated integration work, conflicting interpretations, outdated process knowledge, weak provenance and unsafe automation.

This thesis proposes Orgni, an organisational intelligence infrastructure developed by Olyxee. Orgni converts fragmented organisational evidence and operational activity into a live, governed and temporal model of an organisation.

The model represents organisational entities, relationships, responsibilities, policies, obligations, events, decisions, workflows, evidence and current state. It can then provide trusted and permission-aware context to employees, enterprise applications and AI agents.

Orgni is not intended to be another chatbot, document-management tool, workflow application or general-purpose agent. It is the infrastructure beneath these systems.

The central argument of this thesis is that organisations will require a shared context and state layer as the number of AI agents and specialised enterprise applications increases. Without such infrastructure, every agent will maintain an incomplete and potentially conflicting version of the organisation.

Orgni aims to solve this problem once at the organisational level.

---

# 1. Introduction

Artificial intelligence systems are becoming increasingly capable of performing complex tasks. Modern systems can search private information, generate documents, call APIs, update records, coordinate workflows and interact with external software.

These capabilities are creating a new class of enterprise systems commonly described as AI agents.

An AI agent may be designed to review invoices, answer compliance questions, analyse contracts, support customers, coordinate projects, approve requests or automate internal processes.

However, the effectiveness of an agent does not depend only on the intelligence of its underlying model.

It also depends on whether the agent understands the organisation in which it operates.

To perform work reliably, an agent may need to know:

* which person or department owns a process;
* which policy version is currently active;
* which system contains the authoritative record;
* which approvals are required;
* what happened before;
* what an identifier refers to;
* whether two records represent the same organisation;
* whether an obligation is still active;
* whether information is observed, inferred or disputed;
* what the agent is permitted to access or change.

This information is rarely available as one coherent model.

Instead, it is distributed across contracts, invoices, policies, emails, financial systems, CRMs, collaboration tools, databases and human memory.

The result is that every new AI system must reconstruct its own version of the organisation.

This is inefficient, difficult to govern and dangerous when AI systems begin taking consequential actions.

Orgni is proposed as the infrastructure that creates and maintains a shared organisational understanding.

---

# 2. Thesis Statement

The main thesis is:

> As organisations adopt more AI agents and specialised applications, they will require a shared, governed and continuously updated infrastructure layer that represents how the organisation works.

Orgni is designed to become that layer.

It creates a machine-readable organisational model from evidence and operational events. This model can then be used by humans, applications and AI agents through APIs, software development kits, event streams and the Model Context Protocol.

The objective is not to build one agent that understands one workflow.

The objective is to build infrastructure that allows many systems to operate from the same trusted organisational context.

# 3. The Emerging Problem

## 3.1 Agent development is becoming easier

The technical barriers to creating AI applications are decreasing.

Developers can use hosted models, agent frameworks, retrieval systems, connectors, tool-calling interfaces and workflow orchestration platforms. This allows small teams to create specialised AI products more quickly.

As these tools mature, more companies will create agents for finance, legal work, compliance, customer service, procurement, human resources, software development and operations.

This growth will create a new infrastructure problem.

Every agent will require access to organisational context.

Without a shared context layer, each agent team will independently build:

* connectors;
* retrieval pipelines;
* embeddings;
* prompt instructions;
* memory systems;
* permission rules;
* entity matching;
* workflow representations;
* policy mappings;
* audit mechanisms.

These systems will duplicate work and produce different interpretations of the same organisation.

## 3.2 Organisational information is fragmented

Organisations already store large quantities of information.

The problem is not necessarily the absence of data.

The problem is that the data does not form a shared operational understanding.

For example, information about a supplier may appear in:

* a contract;
* an invoice;
* a procurement system;
* a bank payment record;
* an email conversation;
* a spreadsheet;
* a compliance certificate;
* a CRM profile.

Each source may use a different name or identifier.

A human employee may understand that these records refer to the same supplier. A software system may not.

The information also represents different types of truth.

A contract may state an obligation.

An invoice may assert that payment is owed.

A proof of payment may show that payment was initiated.

A bank record may confirm that payment settled.

These sources should not be treated as interchangeable.

A reliable organisational system must preserve the meaning, evidence and confidence of each claim.

## 3.3 Organisational context changes over time

Organisations are not static.

People change roles. Policies are updated. Contracts expire. Responsibilities move between teams. Systems are replaced. Processes are redesigned. Decisions create new exceptions.

A static knowledge base may describe the organisation at one point in time, but it cannot reliably represent how the organisation changes.

A useful organisational model must distinguish:

* when an event occurred;
* when the system recorded it;
* when a fact became effective;
* when it stopped being effective;
* which version is current;
* what was believed at a previous point in time.

Without this temporal capability, AI systems may act on outdated information.

## 3.4 Organisational truth is uncertain

Enterprise information is often incomplete or contradictory.

Two systems may contain different addresses for the same supplier.

A contract may appear signed in one repository but remain marked as a draft in another.

An invoice may reference a payment, while the bank transaction is still pending.

A policy may have been uploaded without confirmation that it is the current version.

A reliable system should not silently select one source and discard the others.

It should preserve:

* the competing claims;
* their evidence;
* their timestamps;
* their authority;
* their confidence;
* any human review decision.

Orgni therefore treats uncertainty as part of organisational reality rather than an error to hide.

# 4. The Strategic Opportunity

The visible AI market is focused on building agents and applications.

The deeper opportunity is to provide the infrastructure that these systems require.

The number of specialised AI products may increase rapidly, but each product will still need to understand:

* organisational identity;
* operational relationships;
* current state;
* historical events;
* permissions;
* policies;
* responsibilities;
* evidence;
* context.

If every product builds these capabilities independently, organisations will accumulate many disconnected context systems.

Orgni proposes a shared infrastructure model.

Instead of every agent maintaining its own version of the organisation, the organisation maintains one governed operational model that authorised systems can consume.

This changes the architecture from:

```text
Agent A → private context system

Agent B → separate context system

Agent C → separate context system
```

to:

```text
Organisation → Orgni → Agent A

                     → Agent B

                     → Agent C
```

This model reduces duplication and creates a consistent foundation for enterprise AI.

# 8. Source and Ingestion Layer

The first layer receives organisational information.

Sources may include:

* uploaded documents;
* emails;
* APIs;
* databases;
* business applications;
* event streams;
* user corrections;
* workflow systems.

The ingestion layer does not attempt to understand the complete meaning of the source.

Its responsibilities include:

* creating a source ID;
* recording the tenant or organisation;
* calculating a checksum;
* preserving access permissions;
* storing the original source;
* detecting duplicates;
* managing retries;
* recording processing status;
* maintaining an audit trail.

The original source must remain available because all later organisational conclusions must be traceable to evidence.

---

# 9. Interpretation Layer

The interpretation layer reads source-specific information.

For documents, this may include:

* OCR;
* layout detection;
* classification;
* field extraction;
* table extraction;
* evidence localisation;
* confidence scoring.

For an API source, interpretation may involve mapping an external payload into a standard source envelope.

The interpretation layer should report what the source contains.

It should not calculate the complete organisational state.

For example, an invoice may state:

* invoice number;
* supplier;
* buyer;
* amount;
* due date.

The interpretation layer should not automatically conclude that the invoice is currently overdue, because the invoice alone does not know whether it was paid, disputed, cancelled or credited.

---

# 10. Organisational Tokenisation

The organisational tokenizer converts source-specific information into standard organisational claims and observed events.

This separates the original source format from the organisational meaning.

A contract, email or API record may all produce a standard event such as:

```text
CONTRACT_EXECUTED
```

An invoice may produce:

```text
INVOICE_ISSUED
PAYMENT_OBLIGATION_CREATED
PAYMENT_DUE_DATE_STATED
```

A payment record may produce:

```text
PAYMENT_REPORTED
```

The tokenizer should preserve:

* source evidence;
* tenant identity;
* confidence;
* epistemic status;
* effective time;
* transaction time;
* permissions;
* processor version.

The tokenizer must not invent missing information.

It determines:

* which entity types exist;
* which relationship types are valid;
* which event types are recognised;
* which properties are required;
* which states are possible;
* which policies apply;
* which combinations are invalid.

Possible entity types include:

* organisation;
* person;
* department;
* role;
* system;
* document;
* contract;
* invoice;
* payment;
* policy;
* workflow;
* task;
* obligation.

Possible relationships include:

* employed_by;
* reports_to;
* responsible_for;
* governed_by;
* issued_to;
* contract_party;
* satisfies_obligation;
* approved_by;
* stored_in;
* depends_on.

The ontology does not store the entire organisation.

It defines how organisational information should be interpreted and validated.

# 12. Entity Resolution

Entity resolution identifies when different records refer to the same organisational object.

For example:

```text
ABC Technologies
ABC Technologies (Pty) Ltd
ABC Tech
Supplier SUP-0042
Registration number 2021/123456/07
```

These records may refer to one organisation.

Orgni should create a canonical entity while preserving the original source identities.

Entity resolution should use:

1. official identifiers;
2. system-specific IDs;
3. verified contact information;
4. normalised names;
5. addresses;
6. supporting relationships;
7. probabilistic matching;
8. human review.

Automatic merges should prioritise precision.

An incorrect merge can corrupt the organisational model.

All merges should therefore be reversible and auditable.

---

# 13. Claims, Events and State

Orgni should separate three concepts.

## 13.1 Claims

A claim is a statement supported by evidence.

Example:

```text
ABC Technologies issued invoice INV-100 to Olyxee.
```

The claim may be observed, inferred, disputed or superseded.

## 13.2 Events

An event represents something that occurred.

Example:

```text
Invoice INV-100 was issued on 10 July 2026.
```

Events are recorded in an append-only organisational ledger.

## 13.3 State

State represents the current result of previous events and claims.

Example:

```text
Invoice INV-100 is awaiting payment.
```

State should be calculated by a state engine.

It should not be permanently asserted by one document without considering other evidence.

This separation allows Orgni to replay history and reconstruct the organisation at any previous point in time.

---

# 14. The Organisational Ledger

The organisational ledger is the authoritative record of accepted organisational information.

It should contain:

* sources;
* evidence;
* claims;
* events;
* entities;
* aliases;
* relationships;
* ontology mappings;
* entity resolutions;
* conflicts;
* review decisions;
* corrections;
* processing versions.

The ledger should be append-oriented.

Corrections should not erase history.

Instead, a correction should create a new record that supersedes or disputes an earlier claim.

This allows Orgni to answer:

* What is currently believed?
* Why is it believed?
* What was believed before?
* Which evidence changed the conclusion?
* Who approved the correction?

---

# 15. Organisational State Engine

The state engine calculates current organisational state from accepted events and claims.

For a contract-to-payment workflow, states may include:

* contract draft;
* contract active;
* obligation open;
* invoice received;
* invoice approved;
* invoice due;
* payment reported;
* payment matched;
* payment confirmed;
* obligation settled;
* disputed;
* expired.

The state engine should use explicit transition rules.

For example:

```text
INVOICE_ISSUED
+
PAYMENT_DUE_DATE_STATED
+
NO CONFIRMED PAYMENT
+
CURRENT DATE AFTER DUE DATE
=
INVOICE OVERDUE
```

If later evidence confirms payment before the due date, Orgni should update the current state while preserving the previous processing history.

---

# 16. Organisational Graph

The organisational graph represents relationships between organisational entities.

Example:

```text
Olyxee
  has_contract_with
ABC Technologies

ABC Technologies
  issued
Invoice INV-100

Invoice INV-100
  relates_to
Contract CT-2026-14

Payment PAY-201
  matches
Invoice INV-100

Finance Manager
  approves
Invoices above R8,000
```

The graph allows Orgni to answer relationship-based questions.

However, the graph should initially be a projection of the authoritative organisational ledger.

It should be possible to rebuild the graph from stored claims, events and entity-resolution decisions.

---

# 17. Context Engine

The context engine is the layer that makes Orgni useful to applications and AI agents.

An application should not need to retrieve the entire organisational graph.

It should request context for a specific:

* actor;
* task;
* object;
* time;
* permission scope.

Example request:

```json
{
  "actor": "finance-agent",
  "task": "review_invoice",
  "resource": "INV-101",
  "asOf": "2026-07-23"
}
```

Orgni may return:

* supplier identity;
* active contract;
* related obligations;
* invoice details;
* previous payments;
* approval policy;
* responsible approver;
* current exceptions;
* supporting evidence;
* confidence;
* missing information.

This package should be:

* permission-aware;
* evidence-backed;
* time-aware;
* bounded;
* reproducible;
* freshness-labelled.

The context engine is the primary interface between organisational intelligence and external AI systems.

# 23. Development Phases

## Phase 1: Canonical contracts

Create one authoritative schema for:

* source envelopes;
* evidence;
* claims;
* events;
* entities;
* relationships;
* context packages.

Generate TypeScript, validation and Python models from the same source.

## Phase 2: Durable ingestion

Persist:

* original sources;
* metadata;
* processing state;
* evidence;
* extraction results;
* claims;
* events.

Add queues, retries, dead-letter handling and tenant enforcement.

## Phase 3: Ontology runtime

Convert the ontology into an executable validation and mapping system.

Every claim must be accepted, rejected or retained for review.

## Phase 4: Entity resolution

Create canonical identities across documents and source systems.

Include confidence, review and reversible merges.

## Phase 5: Organisational ledger

Store claims, events, relationships, conflicts and corrections in an auditable system of record.

## Phase 6: Graph and state

Build the graph projection and temporal state engine.

Support historical queries and state reconstruction.

## Phase 7: Context engine

Return task-specific organisational context to applications and agents.

## Phase 8: Platform interfaces

Expose REST APIs, SDKs, webhooks, event streams and MCP tools.

# 26. Risks

## 26.1 Becoming a document product

Because the first inputs are documents, Orgni may be mistaken for a document intelligence product.

This risk should be controlled by demonstrating cross-source identity, relationships, state and context.

## 26.2 Becoming a generic knowledge graph

A graph alone does not provide organisational understanding.

Orgni must preserve evidence, time, confidence, state transitions and permissions.

## 26.3 Overbuilding before proving value

The architecture may become too broad.

The first implementation should focus on one complete vertical workflow rather than building every planned module simultaneously.

## 26.4 Incorrect entity resolution

False merges may corrupt the organisational model.

Automatic matching should prioritise precision and preserve human review.

## 26.5 Untrusted inferred state

Orgni must clearly distinguish observed information from calculated conclusions.

Every state should be explainable through claims, events and transition rules.

## 26.6 Enterprise adoption

Enterprises may not initially purchase an abstract context layer.

Olyxee should enter through a measurable operational problem and gradually expand the infrastructure footprint.

# 28. Conclusion

The next phase of enterprise AI will not be defined only by the intelligence of individual models.

It will also be defined by the quality of the organisational context available to those models.

Organisations already possess large amounts of information, but they do not maintain it as one coherent, temporal and machine-readable operational model.

This creates duplicated work, inconsistent agent behaviour and weak governance.

Orgni addresses this problem by converting evidence and operational events into a shared organisational understanding.

Its purpose is to maintain:

* identity;
* relationships;
* obligations;
* policies;
* history;
* operational state;
* evidence;
* permissions;
* context.

Orgni should therefore be understood as infrastructure developed by Olyxee, not as a single application.

The document pipeline, organisational tokenizer and ontology are the first components of this infrastructure.

The immediate development objective is to connect them to a durable organisational ledger, entity-resolution engine, temporal state engine and context-delivery interface.

The defining proof point is simple:

> Orgni should be able to process multiple pieces of organisational evidence, determine how they relate, calculate what is currently true and provide that understanding to an authorised human, application or AI agent.

If this can be achieved reliably, Orgni will move beyond document intelligence and become the foundation for organisational intelligence.
